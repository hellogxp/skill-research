## 一句话总结

本文形式化了 Compositional Skill Routing 问题，提出 SAD 迭代反馈机制使 7B 模型的分解准确率从 51.0% 提升到 67.7%（+32.7%, p<10⁻⁶），并在 transfer 和 human-style 评估中验证泛化性。

## 核心问题（按严重程度排序）

### P0: Human-Style Queries 数据存在严重问题

**问题**: Table 8 (Appendix A) 报告的 human-style 结果 (Vanilla DA=8.5%, SAD DA=21.5%) 极低，论文用"open-ended step boundaries"解释。但实际问题更深层：

1. **Easy queries DA=2.5% (Vanilla)** — 一个标注为 2 个 skill 的自然语言 query，模型合理地分解为 5-8 步。这不是模型问题，是 **ground truth annotation 粒度与自然语言不匹配**。
2. **Relaxed DA±1 仍然只有 30%→48%** — 说明差距不止 ±1 步，模型系统性地产生比 ground truth 多得多的步骤。
3. **论文的解释 ("annotation strictness rather than system failure") 回避了核心问题**: 如果一个评估指标在该数据集上系统性失效，那么报告该指标本身就有误导性。

**风险**: 审稿人会质疑：如果 human queries 上 DA 这么低，为什么要报告它？如果 DA±1 才是正确指标，为什么主文和 compositional 实验不用 DA±1 作为主指标？

**建议**:
- 重新生成 human queries，确保 ground truth 的步骤粒度与模型预期粒度一致（每个 subtask 有独立描述，而非复制全 query）
- 或者：引入 **category-set match** 指标（不依赖步骤数，只看 predicted categories 的 set overlap with ground truth categories），这对 human queries 更公平
- 当前数字 (DA=8.5%/21.5%) 放在论文里弊大于利

---

### P1: CatR@1 提升不显著是根本性弱点

**问题**: SAD 的核心卖点是改善 routing，但下游指标 CatR@1 (34.2%→37.0%) 不显著 (p=0.17)。论文的解释（"SAD 是 granularity corrector, 不是 retrieval precision enhancer"）逻辑自洽，但审稿人可能认为：

- 如果 SAD 只修步骤数而不改善实际 routing 质量，其实用价值有限
- DA=1 conditioned CatR@1 = 41% 仍然很低 — 正确分解后仍有 59% 的步骤匹配不到正确 category
- 论文标题是 "Compositional Skill Routing" 但核心改善在 decomposition counting，not routing

**建议**: 
- 更明确地 reframe：SAD 解决的是 "decomposition-retrieval alignment" 而非 routing precision
- 或增加一个 end-to-end functional metric（如 chain completion 提升），而不只是 pilot study

---

### P2: Baselines 设计不公平

**问题**:
1. **ReAct baseline**: DA=0%，因为 ReAct agent "collapses multi-step tasks into single actions"。但 ReAct 的正常用法不是一次性返回分解结果，而是 iteratively 执行。用 DA 评估 ReAct 是 category error — ReAct 不做 explicit decomposition。
2. **LLM-Direct**: 给 qwen-max 100 个 skill names 让它直接选。CatR@1=21.1%。但这个 baseline 用了一个完全不同的模型(qwen-max vs 7B)，且 "100 skills shown" 的设置是 cherry-picked — 如果给 10 个 skill names 效果会不同。
3. **缺少关键 baseline**: 没有和 ToolLLM/CRAFT/SkillRouter 在同一 pool 上的对比。

**建议**:
- ReAct baseline 应评估其最终产出的 tool calls 是否匹配 ground truth categories，而非 DA
- LLM-Direct 应使用同一模型(7B)以控制变量
- 补充 "Vanilla 7B + cross-encoder reranking" baseline 以隔离 SAD 的独立贡献

---

### P3: Compose 阶段（Stage 3）未评估

**问题**: 论文标题包含 "Compose"，方法描述了 DAG planner + compatibility scoring (Eq.2)，但：
- "This paper focuses on the decompose-retrieve stages" (line 219)
- Compose 阶段没有任何定量评估
- Pilot execution study (Appendix H) 用的是 mock executors

审稿人会认为这是一个 incomplete contribution — 提出了三阶段框架但只评估了两个阶段。

**建议**: 
- 要么去掉 Compose 阶段的方法描述（简化为 future work 一句话提及）
- 要么提供 compose 阶段的 ablation（with/without compatibility scoring 对比）

---

## P4: Template Queries 的 Text Overlap 风险

**问题**: Query construction (Section 4.2) 使用 "template verb phrases combined across categories"。虽然论文声称 "descriptions do not directly copy skill names"，但：
- 未报告 ROUGE-L 或 token overlap 数据
- Paraphrase robustness test 仅 50 queries
- 如果 template 中的 verb phrases（如 "query the database"）与 skill descriptions 有高 overlap，CatR@10=69% 可能被 lexical matching 抬高

**建议**: 
- 报告 query-skill ROUGE-L 或 BM25 overlap 分布
- 扩大 paraphrase test 到全 300 queries

## 次要问题

### 形式问题

1. **Table 1 混合了不同模型和 query 数**: 上半部分是 qwen-max/50 queries，下半部分是 7B/300 queries。这种混合表格容易误导快速阅读者。应分成两张表或用更明确的分隔。

2. **"DA$_{\pm 1}$" 指标出现太晚**: 直到 Limitations 才首次被引用为 human queries 的主要指标。如果它是一个重要指标，应在 Evaluation Metrics (Section 4.3) 就定义并在 main results 中报告。
   - **已修正**: 看到 Table 1 现在包含 DA±1 列了，好的。

3. **Convergence table (Table 3) vs Table 1 的数字不一致**: Table 3 Round 0 DA=0.513 vs Table 1 Vanilla DA=0.510。Caption 解释了 "step-alignment differences in the iterative pipeline"，但这种不一致让人不安 — 应该用同一 pipeline 产生完全一致的数字。

4. **Hardware 声称 "single NVIDIA V100-SXM2-16GB"** — 但 shell history 显示远程服务器有 8 张 GPU。不影响结果（7B 确实只需 1 张），但如果审稿人要求 reproducibility 细节可能会追问。

### 写作问题

5. **Abstract 信息过载**: 7 个数字 (51.0%, 67.7%, 32%, p<10⁻⁶, 34.2%, 37.0%, 35.6%) 在一段内出现。建议精简到 3-4 个关键数字。

6. **"Iterative Skill-Aware Decomposition (SAD)"**: 缩写 "SAD" 不包含 "Iterative" — 实际上默认用单次迭代。命名有轻微不一致。

7. **Section 5.4 "Cross-Model Validation"** 标题用了 `\label{sec:sad-results}`，但内容是 cross-model，label 命名误导。

| 指标 | Abstract | Table 1 | Results text | 一致? |

| Vanilla DA | 51.0% | 0.510 | 51.0% | OK |
| SAD DA | 67.7% | 0.677 | 67.7% | OK |
| Vanilla CatR@1 | 34.2% | 0.342 | 34.2% | OK |
| SAD CatR@1 | 37.0% | 0.370 | 37.0% | OK |
| Transfer DA gain | +35.6% | +35.6% | +35.6% | OK |
| Convergence R0 DA | — | 0.513 | 51.3% | **不一致 with Table 1 (0.510)** |
| Human Vanilla DA | — | 0.085 (avg) | 8.5% | OK (0.025×80+0.112×80+0.15×40)/200=0.085 |
| Human SAD DA | — | 0.215 (avg) | 21.5% | OK (0.112×80+0.35×80+0.15×40)/200=0.215 |

Human-style 数据验证:
- Vanilla avg DA: (0.025×80 + 0.112×80 + 0.150×40) / 200 = (2+8.96+6)/200 = 16.96/200 = **0.085** ✓
- SAD avg DA: (0.112×80 + 0.350×80 + 0.150×40) / 200 = (8.96+28+6)/200 = 42.96/200 = **0.215** ✓
- Vanilla avg DA±1: (0.188×80 + 0.362×80 + 0.425×40) / 200 = (15.04+28.96+17)/200 = 61/200 = **0.305** ≈ 30.0% ✓
- SAD avg DA±1: (0.400×80 + 0.625×80 + 0.475×40) / 200 = (32+50+19)/200 = 101/200 = **0.505** — 论文写 48.3%? 

**注意**: SAD DA±1 计算得 50.5%，但论文写 48.3%。需要验证。可能是我对 weighted average 的理解有误，也可能论文数字有误。

## 审稿人可能追问的关键问题

1. **Q1**: SAD 的 CatR@1 提升不显著 (p=0.17)。如果 SAD 不改善实际 routing precision，它的实际价值是什么？一个只修步骤数的方法为什么不能通过简单的 "output exactly N steps" prompt engineering 替代？

2. **Q2**: Human queries 上 Vanilla DA=2.5% (easy)。这说明什么——是模型太差，还是你们的评估框架与自然语言查询根本不兼容？如果是后者，整个 benchmark 对现实世界的意义何在？

3. **Q3**: Compose 阶段在方法描述中占了大量篇幅（Eq.2, compatibility scoring, DAG），但完全没有评估。如果只评估 decompose+retrieve，为什么不把标题改成 "Skill-Aware Decomposition for Tool Retrieval"？

4. **Q4**: 你说 "metadata suffices for retrieval" (CatR@10=69%)，但 CatR@1 只有 37%。这意味着 top-1 precision 很差。对于实际部署（用户不想看到 10 个候选），这个 37% 够用吗？

## 结论

这是一篇 **实验充分、分析深入** 的 empirical contribution 论文，但存在几个关键弱点：

- **Human queries 数据质量** 是最大风险 — 当前数字 (DA=8.5%) 放在论文里反而削弱了可信度
- **CatR@1 不显著** 限制了 routing 的实际贡献叙事
- **Compose 阶段 + baseline 设计** 可能被质疑

如果能修好 human queries 数据（让 DA 达到 30-60% 的合理范围），论文的整体故事将显著更强。当前状态下，建议在 Limitations 更直接地承认 human query 评估的局限性，并将主文 line 425 的引用弱化或移除。

**总体评估**: Borderline Accept — 技术贡献 solid 但 incremental，数据+评估有需要修复的问题。
