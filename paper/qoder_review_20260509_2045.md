## 核心优势

1. **问题定义精准且有前瞻性**: Compositional Skill Routing 的形式化定义填补了 single-skill routing 到 multi-skill composition 的空白，与 MCP 生态爆发的时间窗口高度吻合

2. **"分解是瓶颈"的洞察有说服力**: Oracle R@1=99.5% vs 7B vanilla CatR@1=33.9% 的对比清晰揭示了问题所在，SAD 的设计直接针对该瓶颈

3. **7B+SAD > 72B vanilla 是强有力结果**: 跨 5 个模型验证，标准差 ≤0.004，结果稳健；这个结论对模型效率研究有广泛启示

4. **诚实透明的 Limitations**: 承认 text overlap、缺 end-to-end 评估、hard queries 下降等问题，符合学术规范

5. **Benchmark 有开创性**: 300 queries + 2595 skills + 17 categories 是首个组合式路由 benchmark，即使有 text overlap 问题，仍为后续研究提供了基础

## 核心问题（按严重程度排序）

### P0 — 致命/极严重问题

**1. Benchmark Text Overlap 严重损害实验有效性**

ROUGE-L=0.845, BLEU-1=0.980, 37.8% exact copies — 这不是"high overlap"，这是"ground-truth 基本是 skill description 的复制品"。这意味着：
- Oracle R@1=99.5% 几乎完全是词汇匹配，而非语义理解
- SAD 的增益可能部分来自 hint 提供了与 ground-truth 相同的词汇线索（skill name → hint → decomposer 复制 → 匹配），形成了一个循环
- 论文中 Appendix F 的 stratified analysis 是好的，但低重叠组 (n=47) 的 SAD 增益 +18.2pp 与高重叠组 +21.9pp 差距不大，反过来说明即使在"低重叠"组 ROUGE-L<0.7 仍然偏高

**这是审稿人最可能攻击的点。** EMNLP 审稿人对 benchmark validity 非常敏感，尤其是当 evaluation 不是 end-to-end 的时候。

**2. 缺少与强执行型 baseline 的对比**

当前 baseline 只有 Single-Skill、LLM-Direct、Oracle Decomposition。缺少：
- **ReAct-style iterative planning**: 让 LLM 反复 plan → execute → observe，这是最自然的 compositional 执行基线
- **Reflexion-style self-correction**: 带反思的迭代规划
- **Least-to-Most Prompting baseline**: 直接用 LLM 做 hierarchical decomposition without retrieval
- 这些 baseline 的缺失让读者无法判断"显式分解+检索"相比"让 LLM 直接规划执行"到底有多大优势

### P1 — 严重问题

**3. SAD 的"vocabulary bridge"假说缺乏机制验证**

论文声称 SAD 的核心机制是 "vocabulary bridge"——将用户查询语言映射到 skill 命名空间。但：
- 没有量化 Pass 2 分解结果的词汇与 skill name 的重叠度变化
- 没有消融"只给 category name" vs "给 skill name"的 hint 效果差异
- 如果 SAD 的效果主要来自 decomposer 复制 hint 中的 skill name，那 SAD 本质上是在"泄露答案"，而非真正改善分解质量

**4. 14B Anomaly 的解释仍是后验假设**

14B < 7B 是反直觉的。论文归因为 "prompt sensitivity"和 "hint anchoring"，但：
- 没有做 controlled experiment 验证（如固定输出格式、用 grammar constraints）
- "intermediate regime" 的解释可以套用在任何异常上，缺乏预测力
- 如果 14B 真的比 7B 差，那 scaling behavior 的 claim 就需要更审慎

**5. Human Hard Queries 性能下降（17.0% → 9.4%）未被充分缓解**

虽然 "hint dilution" 的解释合理，但：
- 10 条样本太少，统计效力不足
- 缺少 adaptive hint selection 的初步实验验证
- 这意味着 SAD 在最需要的场景（复杂组合查询）上反而有害

### P2 — 重要但非致命问题

**6. 图表不足**

只有 1 个主图（TikZ overview）+ 1 个附录图（decomp distribution）。缺少：
- SAD 效果的 t-SNE/UMAP 可视化（分解前后的语义空间变化）
- 难度 vs 性能的 line chart
- hint count vs 性能的 curve（当前只有表格）

**7. 72B+SAD DA 下降的解释不够令人信服**

62.7% → 50.3% 的 DA 下降被解释为 "hint-induced consolidation"，但 CatR@1 仍然低于 7B+SAD。这暗示更大的模型在 SAD 下可能产生不同的失败模式，需要更深入的分析。

**8. 缺少 latency/efficiency 的详细对比**

SAD 需要 2 次 LLM 推理，但论文只提 "~1.6s total on A100 for 7B models"。缺少：
- 与 72B 单次推理的 latency 对比
- 端到端 latency breakdown（decompose → retrieve → compose 各阶段时间）
- 在不同硬件配置下的 scalability 分析

### P0 修改（必须做，影响接受概率 20%+）

**修改 1: 解决 Benchmark Validity 问题**（2-3 天工作量，投入产出比最高）

方案 A（推荐）:
- 用 LLM（如 GPT-4）对 300 条 template queries 的 ground-truth sub-task descriptions 做 paraphrasing，生成语义相同但词汇不同的版本
- 重新跑关键实验（7B vanilla, 7B+SAD, Oracle），报告 paraphrased 版本上的结果
- 如果 CatR@1 下降幅度合理（如 Oracle 从 99.5% 降到 ~80%），而 SAD 的相对增益仍显著，则 text overlap 的质疑被根本性缓解
- 具体实施步骤:
  1. 设计 paraphrasing prompt: "Rewrite the following sub-task description in a different way while preserving the same meaning. Do NOT use any words from the original skill name."
  2. 对 300 queries 的所有 ground-truth sub-task descriptions 进行 paraphrasing
  3. 重新计算 Oracle R@1, 7B vanilla CatR@1, 7B+SAD CatR@1
  4. 对比 paraphrased vs original 结果
  5. 在论文 Section 5 (Benchmark) 中新增 "Paraphrased Evaluation" 段落

**修改 2: 增加 ReAct/Iterative baseline**（2-3 天工作量）

## 与竞品/相关工作的对比分析

| 方法 | 核心区别 | 本文优势 | 本文弱点 |
|------|---------|---------|---------|
| **SkillRouter** | 单技能路由，body 主导 (91.7% weight) | 组合式路由，metadata 匹配 | 只在 metadata 上验证，body 覆盖不充分 |
| **AnyTool** (EMNLP 2024) | 层级自反思导航 API 池 | 可并行执行（DAG），不依赖反思循环 | 缺少与 AnyTool 的直接实验对比 |
| **CRAFT** (ICLR 2025) | 每 query 动态创建工具集 | 不依赖工具生成，更实用 | 未讨论在动态工具集场景下的适用性 |
| **MCP-Zero** | 主动发现 tools，98% token 降低 | 语义路由而非系统层优化 | 未与 MCP-Zero 的 token 节省对比 |
| **ReAct** | 迭代 plan-execute-observe | 分解+检索的归纳偏置更强 | 缺少与 ReAct 的直接对比（P0 问题） |

**关键差异化声明审阅**:

> "All these methods select tools independently per query; none jointly optimizes decomposition, retrieval, and inter-skill compatibility for compositional tasks."

这个声明**部分准确**。AnyTool 和 CRAFT 确实不做 joint optimization，但 ReAct-style 方法隐式地做了 composition（通过 iterative planning）。论文需要更精确地阐述与 iterative planning 方法的区别。

## 审稿人最可能提出的 Questions for Authors

1. **Benchmark validity**: Your template-based queries have ROUGE-L=0.845 with skill descriptions. Oracle R@1=99.5% seems to reflect lexical matching rather than semantic understanding. How confident are you that the relative gains hold on truly naturalistic queries?

2. **Missing strong baselines**: Why no comparison with ReAct-style iterative planning or Reflexion? These are natural baselines for compositional task execution.

3. **SAD mechanism**: Is SAD truly improving decomposition quality, or is it leaking answer information by providing skill names as hints? What happens if you provide only category names instead of skill names?

4. **14B anomaly**: The 14B < 7B result is counter-intuitive. Have you verified this with constrained decoding or different prompt formats? Your "intermediate regime" hypothesis needs independent validation.

5. **Hard query degradation**: SAD degrades performance on hard human queries (17.0%→9.4%). This means your method fails precisely on the most complex cases it's designed to solve. How do you reconcile this?

6. **End-to-end gap**: You evaluate retrieval quality but not execution. What fraction of correctly retrieved skill chains would actually execute successfully?

7. **Scalability**: How would SAD scale to 10K+ skills? The bi-encoder may need retraining as the skill library grows.

## 最终建议

**核心判断**: 这篇论文有好的 problem framing 和一个有力的核心发现（7B+SAD > 72B），但 **benchmark validity** 和 **baseline 不全** 是两个最大的风险点。当前状态投稿 EMNLP 的接受概率约 **45-55%**（Borderline），但如果能投入 5-7 天完成 P0 修改（特别是 paraphrased benchmark + ReAct baseline），概率可提升至 **60-70%**（Accept）。
